Draft · Button · state modifier

CTA beacon c-btn-beacon

A temporary "look here next" cue for the single next step, typically right after an AI fill lands. A ring breathes out of a Primary button three times while its trailing arrow nods, and then it stops for good. The button itself is unchanged: same fill, size, radius, hover and focus outline as shipped.

Anatomy and rules

Anatomy

  1. Host button. A shipped c-btn c-btn-primary c-btn-sm|md|lg with a visible label. Not restyled in any way.
  2. Ring. A box-shadow from 0 to spacing-12, Neutral-9 at 32% fading to 0, every 1.4s. It never takes up layout space.
  3. Nod (optional). Only a trailing ph-arrow-down (nods down) or ph-arrow-right (nods right), moving 3px in step with the ring. No arrow means ring only.

What it is: a state, not a style variant. It is temporary attention that the host switches on, that ends itself, and that leaves nothing behind. It sits in Button's States table as "Beacon (transient)", and the variants section points to it because it is opted into per instance with a modifier class: c-btn c-btn-primary c-btn-md c-btn-beacon.

When to use: once, for the single next step, right after something the user started has finished and the next action has become relevant. Examples: "Next: audience" after the AI fills the Brief, or "Confirm booking" once the slot check passes.

Allowed on

ButtonBeaconWhy
Primary sm / md / lg, labelledYesThe single main action (Rule 2). The ring is the button's own dark ink breathing out. The reach (spacing-12) and nod (3px) are the same at every size, because the icon is always icon-sm and the clearance rule is a single value.
Primary icon-onlyNoNo visible label names the next step. A pulsing square reads as a notification or recording dot. Blocked in CSS.
SecondaryNoCarries shadow-1, which the ring would overwrite, so the shipped look would change. Also, the next step is never a secondary action.
GhostNoLow emphasis, used for toolbar and row actions. It is never "the" next step.
DangerNeverNever draw attention to a destructive commit. (Also, no .c-btn-danger ships in components.css.)
LinkNoNo box or height for a ring to come out of.
Any disabledNever:disabled and aria-disabled="true" are excluded in CSS, and the script refuses to arm them.

States

Stopped (cap reached)The last keyframe is a transparent ring at 0 spread, so it is identical to a plain Primary. The script removes the class.
Stopped (interaction / replaced)The class is removed. A plain Primary.

DisabledThe shipped disabled look. Never beacons.

Stop conditions

  • Cap: animation-iteration-count:3. It ends with no JavaScript at all, and the reduced-motion hold is a single 4.2s iteration with the same cap.
  • Hover, focus, press: the CSS mask hides it instantly using !important, which outranks the running animation without resetting its clock, so leaving hover cannot replay fresh rings.
  • Permanent: the host script removes the class on the first pointerenter, focus or click, and on animationend. Once ended, it never restarts by itself.
  • Without JS: the cap still holds. Hover and focus only hide it while they last, and if the 4.2s window is still running it shows again afterwards. Hosts should ship the script.
  • Re-arm: host only, for example after the next AI fill lands. CBeacon.arm(btn) removes the class, forces a reflow and adds it again, so the animation restarts from ring 1.

Host contract

  • CBeacon.arm(btn) refuses unless the button is Primary, not icon-only and not disabled. It disarms any other armed beacon first (one per screen). Then it arms and listens for a stop.
  • CBeacon.disarm(btn, reason) removes the class and its listeners.
  • Each change fires a c-btn-beacon-change event on the button with {armed, reason}. Reasons: hover, touch, focus, click, cap, replaced, host.
  • Never call focus() as part of arming.

Accessibility

  • Purely visual. No live region, no aria-describedby, and no change to the accessible name. The arrow is aria-hidden.
  • Nothing else is needed for assistive tech. The button is already in the tab order, and its label ("Next: audience") already says what comes next. If the AI fill itself needs announcing, that is the fill's job, not the beacon's.
  • Never move focus to a beaconed button.
  • WCAG 2.2.2: the motion lasts 4.2s, under 5s. WCAG 2.3.1: a soft fade at about 0.7 per second, with no flashing.
  • The ring carries no information, so 1.4.11 doesn't apply. The button's own contrast is unchanged.
  • Reduced motion: a steady 2px ring for the same window (recommended over nothing, because a still cue keeps the intent and adds no motion).
  • Forced colours: the ring is removed and nothing replaces it. An outline would falsely signal focus.

Surfaces and limits

  • Light neutral surfaces only: Neutral-1, Neutral-2, canvas-warm, canvas-warm-card. Verified below on canvas-warm and on a white card.
  • Not on dark surfaces (for example Hero Card's AI surface on Neutral-8). Neutral-9 ink on Neutral-8 is invisible (see the Don't specimen), and an inverse ring would be a new colour decision, flagged rather than invented.
  • One beacon per screen, enforced by arm().
  • Only the single next step. Never on destructive actions, never permanent, and never on disabled buttons.
  • Clipping: an overflow:hidden ancestor closer than spacing-12 crops the ring. It degrades gracefully, but keep the clearance.

Relation to other Button variants

  • Works orthogonally to the colour variants and sizes, but is valid only on Primary. Like Loading, it sits on top of a variant rather than replacing one.
  • It does not compete with Primary's one-per-region rule: the beacon marks the Primary that is already there.
  • Focus-visible (2px Obsidian outline) and the beacon never show together. Focus masks and disarms it.
  • The step-indicator pulse doesn't exist. The scan note says the rings are "the step indicator's own pulse recipe reused". Stepper's indicator is static, and neither components.css nor DESIGN-SYSTEM.md has a pulse or ring @keyframes. The only "expanding ring" mention is the Fire element motif. So c-btn-beacon-ring is a new recipe.

Do / Don't

Do

  • Arm it on one Primary, right after the step that makes it relevant (for example, an AI fill landing).
  • Pair it with a trailing arrow that points where the next step is.
  • Keep spacing-12 clear around the button.
  • Re-arm only when a new reason arrives.

Don't

  • Put it on page load, on a timer, or on more than one button.
  • Use it on Danger, Secondary, Ghost, icon-only or disabled buttons.
  • Move focus to it, or announce it.
  • Loop it, or raise the count above 3.
  • Use it on dark surfaces.
