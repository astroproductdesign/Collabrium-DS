Note Pin

A compact annotation indicator for table and list rows — attach up to four coloured notes to a single record. Every dialog below is live: open a stack, add a note, edit one, delete one, and the row’s pin count updates.

States

One note keeps its own 48.94 × 54.83. Every stack is 48px tall regardless of count — each stacked card is 42 × 48 and steps 16px, so the container is 42 + 16(n−1), which lands on 58 / 74 / 90 exactly. No white outline between cards: they overlap directly, newest on top. Four notes is the maximum, so 90px is the widest this component ever gets.

Below, the same four states on a dark surface — the fills carry their own contrast, so nothing about the pins changes.

Notes — decisions made, and what needs yours

  • Four notes is the maximum — now a stated rule. Enforced in three places rather than one: the model refuses a fifth, the add button goes disabled + aria-disabled with a plain-English reason, and the stack dialog swaps its “Add a note” action for the cap message. It also bounds the component — 90px is the widest a Note Pin cell ever gets, so a table column can be sized for it and never reflow. Deleting a note re-enables Add immediately.
  • Removing the outline makes two same-coloured neighbours merge. With the hairline gone, cards separate by colour alone — which works because they overlap by 26px of a 42px card, so each one shows a clean 16px band of its own fill. The exception is two adjacent notes the author gave the same colour: they read as one wider card, and the count is only recoverable from the aria-label. Not a problem in the demo data, but reachable in a minute of clicking. Worth deciding whether the colour picker should grey out a colour already used on that row.
  • Single-pin mode is a dead end. needs your call
    Per spec, 0 notes shows an add button and 2–4 notes show a stack plus an add button — but 1 note renders “the button directly without a wrapper”, so there is no add button at exactly one note. A user who adds their first note can never add a second. Row 2 in the table demonstrates it. The checkbox above the table turns on the proposed fix — wrap single-pin mode in .ncell with an add button, making the wrapper universal and the rule “stack when 2–4” rather than “wrapper when 2–4”. Toggle it and compare; I’ve left it off so the default matches what you wrote.
  • Green isn’t the only card that wants obsidian text. your call — built as specified
    Your instinct on green is right, and by a wide margin: white on #00C26E is 2.35:1, obsidian is 6.02:1. But the same test flags two more. Card text is caption/12px, so it’s normal text and the bar is 4.5:1, not 3:1 — navy + white = 4.54:1 (passes, just), orange + white = 3.15:1 (fails), pink + white = 2.49:1 (fails badly). Swapping those two to obsidian fixes both: pink would be 5.68:1 and orange 4.50:1. So the rule that actually holds is “obsidian on everything except navy”, not “white except green”. Built as you specified; say the word and pink and orange flip.
  • All four glyph colours are below the contrast floor. your call — built as specified
    Measured against their own fills: navy #0051AE on #1473E6 is 1.66:1, orange #BE2E00 on #FF5825 is 1.86:1, pink #C23154 on #FF7A90 is 2.19:1, green #007B52 on #00C26E is 2.26:1. WCAG asks 3:1 for non-text, so the pin glyph is the part that would fail an audit — it goes soft on a dim screen, in sunlight, or for a low-vision user. Two things soften the risk: the glyph carries no unique information (the button’s aria-label does, and the fill colour is the real signal), and the coloured rectangle itself is clearly visible against the row. So this is a legibility choice rather than a functional break, and it’s a reasonable one if you want the tone-on-tone look. The comparison row shows the passing alternative per colour if you’d rather close the gap; the fills would stay exactly as they are.
  • The glyph darks are four new values either way. Fills come straight from tokens.css, which resolved the off-palette problem from the last round. #0051AE, #C23154, #007B52 and #BE2E00 don’t exist in the system. Two ways to land them: name them as a documented dark step in tokens.css, which starts a shade ramp this system doesn’t have and that other components would then want; or keep them local to Note Pin. I’d keep them local until a second component needs a dark step — the same call the DS already made for Hero Card’s dark-surface overlays.
  • Is a pin’s colour chosen, or is it its position? needs your call
    The spec says both. The stack markup hardcodes el-0…el-3 in DOM order, which makes colour positional — the first pin is always navy. But the add dialog has a four-swatch colour picker, which makes colour a property of the note. They can’t both hold: if colour is positional, the picker’s choice is discarded the moment the note is saved. I built colour as per-note, since a picker that doesn’t stick is worse than no picker. Consequence, visible in the GRABCAR row: the pile reads orange-green-pink-navy, not navy-pink-green-orange, because the notes are newest-first and the newest happens to be orange. If you want the tidy left-to-right ramp the markup implies, the picker has to go.
  • The sizes aren’t on any scale. 48.94 × 54.83px is sub-pixel and reads as measured off a design tool rather than authored; 8px radius is not a radius token (sm is 12px). Built exactly as given, but worth rounding to 48 × 56 before this is committed — the pin is a hand-rotated object, so nothing depends on the fractional part.
  • Three notes has no specified width. The size table gives 1, 2 and 4. Rather than hardcode two widths I derived it — calc(26px + 16px * n) — which reproduces both given numbers exactly and yields 74px at three. Delete a note from the four-pin row to see it.
  • The DS has no dark theme. needs your call
    tokens.css defines one light palette; nothing in preview.html responds to prefers-color-scheme. The brief asked for dark support, so this draft carries a local override block — but promoting it would make Note Pin the only dark-aware component in the system. Good news from the fill change: the pins themselves now need no dark-mode handling at all, because a full-strength fill on its own rectangle carries its contrast whatever sits behind it. The override that remains is only for the surrounding chrome — table, dialogs, text. So this is now a question about the system, not about this component.
  • Everything but the pins is an existing component. All three dialogs are .c-modal + .c-modal-head/-body/-foot, the add button is .c-icon-btn, dialog actions are .c-btn, the cap tooltip is .c-tooltip-wrap + .c-tooltip-bubble, and the demo table is .c-table. New CSS is the pins and the note-list rows.
  • The disabled add button needed a wrapper to be hoverable. A disabled button fires no pointer events, so its tooltip would never appear. Rather than strip disabled — which would put a dead control back in the tab order — the tooltip listens on the surrounding .c-tooltip-wrap. Both disabled and aria-disabled="true" are kept, as specified.
  • Icons load as CSS, not the JS bundle. The brief specified src/index.js; this uses the two stylesheet links, which is what preview.html already loads. Same icons, and it avoids a second copy of Phosphor when the component lands there.
  • Timestamps. Rendered as “4 Sep 2026, 10:12” via Intl.DateTimeFormat — the spec said “formatted timestamp” without fixing a format, and nothing in DESIGN-SYSTEM.md specifies one. If there’s a house format, say so and it changes in one place.
