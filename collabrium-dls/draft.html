Draft — not in the system yet

Format card

A catalogue tile for an ad-format library: one card per format, each showing a live miniature of how the unit behaves on a page, what it is for, and what it costs to run. Built entirely on tokens.css and components.css as they ship — nothing in either file has been edited.

Use case

Media planners pick formats from a list of forty-odd options whose names mean nothing until you have seen one run. A table of names and sizes does not tell you what a “3D Float-flip” is; a still screenshot barely does better, because the whole difference between one format and the next is what happens over three seconds. This card's job is to make that difference visible before anyone opens a spec sheet.

Use it when

  • The reader is choosing between formats they cannot be assumed to know by name.
  • Behaviour over time is the distinguishing feature — expand, flip, fill, stick.
  • A separate control on the page collects across cards — a compare tray, an “Add 3 to brief” action. That is what earns the compare toggle; without somewhere for the additions to go, it is a dead control.

Don't use it when

  • The reader already knows exactly which format they want — a Table is faster to scan and sorts by size and benchmark, which this cannot.
  • There is nothing to animate. A card whose preview never moves is a base Card with a picture in it, and should be one.
  • Fewer than about four formats are on offer. A grid of two is a decision that should have been a pair of radio buttons.

Where it sits in the system. This is a Card variant, not a new component family — it extends .c-card, .c-card-interactive and .c-card-selectable and adds three parts they do not have: the preview stage, the title row's tag slot, and the rest/spec swap. It takes the Card grid contract unmodified (auto-fill + minmax, align-items:stretch, height:100%), with its own min-width floor of 300px against the base Card's 240.

The component

Hover or tab into a card to play its preview and swap the tagline for the spec. Press + in the top-left corner to add a format to the compare set — the chip fills Obsidian and its glyph becomes a check, and the count below is the tray that justifies the control existing at all. Press it again to remove.

Adding one docks the real Compare bar to the bottom of this window — that is the tray, and it is what earns the toggle. It holds four.

Variant

Expanded — Format panel

The same record the card summarises, opened out: the preview at a size you can actually read, the facts a planner needs before quoting, the supported sizes drawn to scale, and a way out to three formats that do a similar job.

It is rendered inline here on purpose. In use it is a right-hand panel over the library; in a draft it is a thing to sit and look at, and a surface you have to open first is a surface you cannot fine-tune. Use ← and → in the panel head to page through all eight formats, or click any card in Also consider.

Why a panel and not a modal

The system is explicit about this. Modal / dialog's own Don't reads: “use a modal for anything that isn't a focused, single decision — long forms or multi-step flows need a full page or panel, not a modal.” This surface is six sections of reading with two exits; it decides nothing. So it takes Card's fill, radius and border at Modal's elevation, but it is a panel, and it should not trap focus or take aria-modal.

There is a real counter-argument: Tutorial Modal is the one documented exception, carved out precisely for “reads rather than decisions” that collect no input and can be abandoned with nothing lost — which describes this too. If the team would rather this were modal, that exception is the door, and it should be widened in DESIGN-SYSTEM.md rather than quietly reused.

Companion component

Compare formats

What the bar's Compare opens. Two to four formats, one column each, every fact the panel carries laid on the same row so the differences are read across rather than remembered between screens. It ends in one action — the plan — which is the whole reason the comparison exists.

The bar's rule is 2–4, and it is enforced in three places: Compare is disabled below two, every unselected + goes disabled at four, and this view refuses to open outside that range rather than rendering a one-column comparison.

Each sets the bar's selection too, so the whole path is real — bar, modal, and back.

Why this one is a modal

The Format panel above is not, and the difference is worth stating precisely, because both surfaces show much of the same data. Modal's Don't sends “long forms or multi-step flows” to a panel. This is neither: it has no steps, collects no input, and ends in a single decision — which of these goes into the plan — made against evidence assembled for that decision and nothing else. Long content is not a long flow. So it takes the lock in full: scrim, focus trap, Escape, scroll lock, and focus handed back to the control that opened it.

The panel fails that test on its own terms — it decides nothing, so nothing justifies taking the page away from you to read it. Same data, different job, different surface. That distinction is what DESIGN-SYSTEM.md should record, rather than the current wording, which only separates by length.

The one real design decision: what “best” means

A winner can only be crowned when the cells measure the same thing. Your markup marks both Benchmark cells “highest” where both read CTR >0.25% — but that is a tie on a floor, not a maximum, and across the wider library the column holds 68% VTR, 2.1% Engagement and 82% Viewability. Those are four different metrics in one column, and the largest number in it means nothing.

So the mark is computed, and it is withheld on purpose. It appears only when every column in that row parses to a number, every unit is the same, and the values differ — a tie is not a winner. On the current data that lights up Inventory (all in millions per month) and Benchmark only among formats reporting the same metric. CPM is never crowned: cheaper is not better without a brief saying so.

The honest fix upstream is to split Benchmark into a metric and a value — then the column is comparable by construction, and the modal can group or hide the rows that are not.

Five parts. Two of them (the checkbox and the card shell) are existing components used verbatim; three are new.

Content rules

FieldRule
SizesComma-separated, ascending by area, always. Held as structured data and sorted at render, not typed as a string — an ordering rule that depends on whoever typed the list is not a rule. An expandable sorts on its collapsed size, because that is the slot it occupies on the page, and carries its expanded size with it (300×250 → 300×600). An aspect ratio has no area, so it sorts on the ratio, running portrait → square → landscape.
BenchmarkA figure with its unit (0.42% CTR, 68% VTR) or the phrase Not published — never blank, and never a zero standing in for “unknown”.
FamilyTag label, 24 characters maximum per Badge & Tag's own authoring limit. The component never truncates; a longer family name gets rewritten.

Decisions on record

Every question this draft raised has been ruled on. Nothing here is being promoted — this stays a draft, and no change has been made to tokens.css, components.css or DESIGN-SYSTEM.md. The rulings below are scoped to this component and are recorded so the reasoning is not re-litigated the next time someone opens the file.

2. A format family is a Tag — for this component. Settled. Badge & Tag defines Tag as labelling which element/department owns something, and a format family is a taxonomy rather than an owner. That reading is noted and set aside: within the Format card, family is a Tag.

What that does not mean is a widened definition upstream. DESIGN-SYSTEM.md is not being edited, Tag’s documented meaning is unchanged, and no other component inherits this from here. The six-way mapping is fixed and recorded under Families above, which is what keeps the colours from drifting card to card; .c-tag-purple stays local to this draft.

2b. The compare control keeps the round +/✓ at top-left — specific to this component. Settled. Card Selectable specifies an 18×18 Checkbox at the card’s top-right (DESIGN-SYSTEM.md:2282). This card diverges on both counts, deliberately, and the divergence stays inside this component — Card Selectable is unchanged and nothing is being written back to the system.

Position. The rule’s own justification is “the exact same position and recipe as Profile card’s” — and Profile card puts it top-right because its top-left is occupied by the avatar. This card has no such constraint, and top-left is the corner its preview leaves free.

Control. A checkbox says this one is included; a + says put this somewhere. With a compare tray as the destination, add/remove is the truer verb pair. Both poses are built from the real Button component — Secondary at rest, Primary when on — so nothing about it is bespoke except the circle, for which .c-prompt-bar-mark is already the precedent.

One measurement kept on the record: the resting chip’s 1px Neutral-3 border is 1.43:1 against the white page mock, under the 3:1 UI floor. It passes because the boundary is not what identifies the control — the + glyph is, at 20.03:1 — and the check on Obsidian is 14.14:1. Stated so it is a known quantity rather than an oversight.

3. No screen-reader-only utility. Closed. The system does not have one and is not getting one on this draft’s account. Nothing here needs it: every icon-only control carries a real aria-label, the compare bar’s count is a live role="status", and the comparison table names its rows with <th scope="row"> — all visible text doing the work, which is the better answer anyway.

4. “Not published” stays plain text. Closed. It will not become a Badge or a status. An absent benchmark is a gap in the record, not a state of the format, and dressing it as one gives a missing number more presence than the numbers that exist. It keeps the same treatment every other absent value gets — written out, one step lighter, at regular weight — so it reads as “nothing here” at a glance down a column and nowhere else.
