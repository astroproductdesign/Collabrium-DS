Draft — not in the system yet

Format card

A catalogue tile for an ad-format library: one card per format, each showing a live miniature of how the unit behaves on a page, what it is for, and what it costs to run. Built entirely on tokens.css and components.css as they ship — nothing in either file has been edited.

Use case

Media planners pick formats from a list of forty-odd options whose names mean nothing until you have seen one run. A table of names and sizes does not tell you what a “3D Float-flip” is; a still screenshot barely does better, because the whole difference between one format and the next is what happens over three seconds. This card's job is to make that difference visible before anyone opens a spec sheet.

Use it when

  • The reader is choosing between formats they cannot be assumed to know by name.
  • Behaviour over time is the distinguishing feature — expand, flip, fill, stick.
  • A separate control on the page acts on a multi-card selection (a compare tray, an “Add 3 to brief” action). That is what earns the checkbox — see the note under Anatomy 2.

Don't use it when

  • The reader already knows exactly which format they want — a Table is faster to scan and sorts by size and benchmark, which this cannot.
  • There is nothing to animate. A card whose preview never moves is a base Card with a picture in it, and should be one.
  • Fewer than about four formats are on offer. A grid of two is a decision that should have been a pair of radio buttons.

Where it sits in the system. This is a Card variant, not a new component family — it extends .c-card, .c-card-interactive and .c-card-selectable and adds three parts they do not have: the preview stage, the title row's tag slot, and the rest/spec swap. It takes the Card grid contract unmodified (auto-fill + minmax, align-items:stretch, height:100%), with its own min-width floor of 300px against the base Card's 240.

The component

Hover or tab into a card to play its preview and swap the tagline for the spec. Tick a card to select it — selection is persistent, and the toolbar count below is the bulk-action context that justifies the checkbox existing at all.

Anatomy

Five parts. Two of them (the checkbox and the card shell) are existing components used verbatim; three are new.

#PartSpec
1Preview stage
.c-format-stage		New. 16:10, full-bleed to the card's inner edge, canvas-warm ground under a Neutral-1 page mock at radius-sm + shadow-1. Bleeds rather than insets because an inset stage needs a nested radius of radius-lg − spacing-16 = 4px, and 4px is not a token — bleeding lets it take the card's own radius-lg and invent no new shape. Decorative: aria-hidden="true", and the format's name and behaviour are carried in text below it.
2Select checkbox
.c-card-select		Existing, verbatim. Card Selectable's own recipe — 18px .c-checkbox-box, spacing-16 inset, hidden at rest, revealed on hover, persistent once checked. One addition: a Neutral-1 backing plate, because here it sits over a preview rather than over the card's own white padding, and a 1px Neutral-3 outline is not reliably visible against an arbitrary mock.
3Play hint
.c-format-hint		New, and conditional. Renders only under @media (pointer:coarse). A touch device has no hover, so without it the preview simply never moves and the card reads as broken rather than as resting. On a fine pointer it is suppressed — a label telling you to do the thing you are already doing is noise.
4Title row
.c-format-titlerow		New container, existing contents. Card's own h5 type token for the title, and the real Tag component for the family. The title is an <a> with a stretched ::after covering the card — that is what makes the whole card clickable, without a role="button" wrapper. spacing-24 right reserve on the tag, held at rest as well as on hover, per Card Selectable's own rule.
5Rest / spec swap
.c-format-swap		New. Two blocks stacked in one grid cell, cross-fading on duration-base. At rest: tagline (body2/Neutral-5) + funnel stage (label3 eyebrow). On hover or focus-within: Objective, Sizes, Benchmark as a <dl>. Both halves stay in the DOM and in the accessibility tree — only the paint swaps. Under pointer:coarse it stops being a swap and becomes two stacked blocks.

Why the preview rests. Twelve cards all animating at once is a grid nobody can read, and it is a battery cost on a page that is mostly being browsed. Each stage plays only while the card is hovered, focused within, or tapped — driven by a single --play custom property flipped between paused and running, so every format's animation obeys one switch rather than each one wiring its own.

Tokens used

No raw values, per Component Rule 3. The two exceptions are called out below and both are derived from tokens rather than chosen.

RoleToken
Card shell--radius-lg, --spacing-16, --shadow-1 / -2 / -3 / --shadow-focus, --color-neutral-1 / -3, --color-obsidian
Stage--color-canvas-warm ground, --radius-sm page mock, --color-neutral-2 / -3 / -4 wireframe
Type--text-h5-* title, --text-body2-* tagline and values, --text-label3-* eyebrows, --text-caption-* hint
Motion--duration-base + --ease-standard swap; --ease-morph flip; --ease-settle sticky arrival; --duration-fast checkbox reveal
Family tags.c-tag-water / -fire / -wood / -earth, as they ship

Derived, not invented: the stage's inner radius is calc(var(--radius-lg) − var(--fc-bw)) — the inside edge of the card's own border, which moves correctly when Selected swaps 1px for 2px. The wireframe's 3–6px bar heights inside the page mock are sub-token because the mock is a drawing of a page at ~12% scale, not a UI surface; treating them as spacing tokens would be a category error.

Open questions before this goes in

1. Tag contrast fails AA — and this is a pre-existing system issue, not a draft one. Component Rule 5 says contrast is checked, not assumed, so I measured all five Tag variants as they ship in components.css: element colour on that element's own -bg tint, at caption size (12px, weight 700 — body text, so the 4.5:1 floor applies).

TagPairMeasured4.5:1
Water#1473E6 on #E8F1FD3.99:1fails
Fire#FF5825 on #FFEEE92.80:1fails
Wood#FF7A90 on #FFF2F42.28:1fails
Earth#00C26E on #E6F9F12.15:1fails
Gold#FFA425 on #FFF6E91.85:1fails

Badge already solves this for two of its variants — its Success and Warning text are documented as “darkened for AA”. Tag never got the same treatment. The fix is the same one: a darkened text step per element, dot and fill unchanged. That is a components.css change and is not in this draft, because you asked me not to touch the system files. The draft uses Tag exactly as it ships so the gap stays visible rather than being papered over here.

2. Is a format family really a Tag? Badge & Tag defines Tag as “labels which element/department owns something”. A format family — Interactive, Rich media, Video, Standard — is a taxonomy, not an owner: every format on this page is owned by CollabMedia, so colouring by owner would make all four cards Water and say nothing.

I used Tag anyway, because the alternative is a sixth pill component and Rule 2 already makes element colour the classifying signal. But it does stretch the definition, and the honest options are: (a) widen Tag's definition in DESIGN-SYSTEM.md to “ownership or classification”, (b) record a fixed family→element mapping so the colours are at least stable, or (c) drop the colour and use a Neutral tag. Your call — I would take (a) plus (b).

3. The system has no screen-reader-only utility. This draft defines a local .vh class for the checkbox's label. Several existing components need one too and each currently works around it. Worth adding once to components.css.

4. Benchmark is sometimes “Not published”. Rendering an empty value as a phrase is right, but it means the Sizes row and the Benchmark row carry different kinds of fact at the same weight. If the benchmark is usually missing, it should probably be a Badge (a status) rather than a spec value.
