The white box around the tick — found the actual cause, fixed it

My first theory here was wrong, so I'm correcting it rather than letting it stand: I initially assumed this was a font-loading race (the icon font not ready when the page paints, browser substituting a local fallback). I built a "hide until confirmed loaded" guard for that theory — then tested it and the white box was still there, which meant the font was loading fine and the theory was wrong. Rendering the actual vector paths directly (no font involved at all) settled it: ph-fill ph-check and ph-fill ph-x are not bare marks. In this icon set, "Fill" weight for a line-only glyph like check or X means a solid rounded-square badge with the mark cut out of it — a checkbox icon, not a checkmark icon. That square is the real, correctly-rendered glyph; it was the wrong icon choice on my part, not a rendering bug. Warning's triangle looked fine throughout because a triangle already has a natural fillable shape, so "Fill" weight didn't need to invent a frame for it — only Check and X, both open line strokes, got one.

Fix: switched Completed and Error to the Bold weight (ph-bold ph-check, ph-bold ph-x) instead of Fill — a bare, thick checkmark and thick X, no frame, matching Warning's already-correct bare triangle. Verified by rendering all three side by side before touching the real markup. This needed one addition: a <link> to Phosphor's Bold stylesheet alongside the existing Regular/Fill ones already loaded here and throughout the rest of the system. I also kept a small, unrelated font-load guard in place (the three flag glyphs stay invisible until the browser confirms the icon font has loaded, rather than ever flashing a wrong fallback) — genuinely cheap insurance against a real but separate risk, not the fix for this specific bug.

Description slot — Error / WarningThe flag's message replaces the step's normal description on the same line — never adds a second line beneath it. Error — validityValid only when the step it's on is Active. An Error on an Upcoming step asserts a failure for something never attempted; an Error on a Completed step contradicts "completed." Enforced in code (see the Enforcement section below), not left to whoever calls the component correctly

Warning — validityValid only when the step it's on is Completed. Variants: orientation (Horizontal / Vertical) and per-step description are independent, giving Horizontal/Vertical × With/No description as four presentations, not four hard-coded variants.

Do: derive each step's state from a single currentStep index — before it is Completed, at it is Active, after it is Upcoming — then layer Error/Warning/Disabled on top as flags on a specific step, never as a fourth or fifth value in the state enum itself (that reintroduces per-step tracking and makes two simultaneous "Active" steps reachable again). Enforce Error-on-Active-only, Warning-on-Completed-only, and at-most-one-Error in code, not just in this table. Let the flag's message replace the step's description on the same line, the way Input Field's error text replaces its helper. Give each flagged/status glyph a different shape (check / warning-triangle / bare x) so the three survive greyscale and don't rely on color alone. Use Red text for Error and Badge's own --color-neutral-9 for Warning message text, and the saturated tokens for the indicator fill itself.

Don't: let the connector's length or spacing depend on label or description length; both orientations keep it fixed/equal on purpose. Don't put a Warning on the Active step or an Error on an Upcoming one — neither means anything (whatever's wrong with the current step belongs in that step's own UI; nothing has been attempted on a step not yet reached). Don't put the flag message in the description slot — descriptions are all-or-nothing across the whole stepper, and a flag appearing there mid-flow would force a description onto every other step too. Don't let a Warning gate progress — if it has to be acknowledged before continuing, it's an Error, not a Warning. Don't auto-advance when an Error clears; resolving and advancing are two separate acts. Don't draw a normal, uninterrupted-looking connector out of a step that's currently blocking forward progress.

Enforcement — checked in code, not just documented

validateStepFlags() below is real, running JS — open devtools and re-run it yourself. It checks three things on a step array before anything renders: Error only on the Active step, Warning only on a Completed step, and at most one Error total. The valid example passes silently; the invalid one is caught and its exact rejection reason is printed, not just asserted in prose.

Answers to what you asked

  • Error / Incomplete / Disabled — did we have them? No. Before this draft, only Completed/Active/Upcoming existed, in both DESIGN-SYSTEM.md and components.css. Error and Disabled are added above as new proposed states. "Incomplete" — I've treated this as the existing Upcoming state (a step not yet reached), since that's the closest match already in the system and nothing called "Incomplete" existed separately. If you actually meant something else — e.g. a step the reader visited and left with missing/invalid fields, distinct from one they haven't reached yet — that's a real fourth state I haven't built, not a renaming of Upcoming; let me know and I'll add it properly rather than overload Error for it.
  • Was it optimized for mobile? No @container/@media rules existed for .c-stepper before this draft — that part's a plain fact. But I initially over-claimed what that gap actually meant: my first pass here asserted horizontal .c-step's hardcoded 24px column would let .c-step-text collide with its neighbor on a phone, and I built a "before/after" comparison around that story. When I actually measured the two text boxes' bounding rects instead of eyeballing a screenshot, there was no overlap — down to 240px container width, even with longer labels/descriptions than the real demo uses. Text wraps instead of running wide, which self-limits each column far more than the raw CSS suggested. So: nothing was actually broken, and I've corrected the draft rather than leave that claim standing. What I kept is a smaller, honest improvement — hiding descriptions and adding a label-truncation safety net below 480px of the stepper's own container width — framed as a density/scannability choice, not a bug fix. Vertical orientation needed nothing either way; it's already a single column.
