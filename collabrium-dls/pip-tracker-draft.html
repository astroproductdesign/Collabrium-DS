Pip tracker c-progress-pips

A quiet, read-only track of discrete pieces: one small pip per piece, each done, needing a fix, in draft or not started, with a "3/5" count beside it. Ported from the Collab:Sales Home campaign queue, where the five pips are the five pieces of a pitch: Brief, Research, Big idea, Package, Deck.

Recommendation

Ship it as a Progress Bar variant, "Stepped (pips)", with its own root class .c-progress-pips. Don't build it on .c-progress-track, and don't make it a standalone component.

  • Why not .c-progress-track.stepped: the shipped track is full-width, filled with Neutral-3, overflow:hidden and outlined in forced colours. Pips need a transparent track with gaps, their own width and their own forced-colours shapes. Using the track class would mean overriding four shipped declarations, which counts as restyling it.
  • Why it's still Progress Bar: it uses the same language without changes. Neutral-3 for unfilled, Obsidian for done, radius-pill, an 8px gap between track and label, a caption label, read-only, and it takes on its parent's hover. It never turns green by itself.
  • Why not Stepper: Stepper shows a flow with one Active step, using numbered 24px circles and labels. Pieces can be done in any order and are read at a glance.
  • Different accessibility model: Progress Bar uses role="progressbar" with a 0–100 value. Pips are discrete, and each has its own state, so the tracker is one role="img" with a full sentence as its name.

Deviations from Progress Bar docs

To add to Progress Bar's section on promotion, under the Stepped (pips) variant:

  • Intrinsic inline width. Progress Bar's Placement rule says "always full width of its parent, never an intrinsic inline width". Pips are a fixed 12px each, so the tracker takes its own width.
  • Count style. Caption / weight-bold / Neutral-9, not the trailing label's caption / 400 / Neutral-5. The count is the figure a reader scans for in a row. Open question 4.
  • Role. role="img" with a sentence aria-label, not role="progressbar" with aria-valuenow. A single value can't express per-piece states.

In context: campaign queue

Built from the shipped Lists parts as they ship: static div.c-list-item rows (a row holding a button is static, per Lists rule 5), a 32px .is-logo lead, a heading plus a caption ("MILO · due 14 Oct"), and the trailing slot. The trailing slot holds the pips, the next-step block (showcase-only, and out of scope: scan item 9) and a Secondary sm button. Nothing navigates.

Narrow widths, by the queue's own width (container query, not the viewport): from 960px everything shows. Below 960 the next-step block drops. Below 560 the track drops to count only and the CTA becomes icon-only. The source hid the tracker completely below 1100px. We recommend keeping the count: it's 24px wide, and the row's name still reads the full sentence.

Two host recipes for count only:

  1. Toggle the class. The host adds or removes .is-count-only on the root, from JS or server-side when it knows the slot is narrow.
  2. From the host's own @container. The host hides .c-progress-pips-track with the same declaration, because a container query can't add a class. This mock uses this one: @container queue (max-width:559px){ .sc-queue .c-progress-pips-track{display:none;} }.

Either way the root's aria-label stays the same.

Do and don't

Do

  • Keep each piece in its own fixed position, so Package is always pip 4 and the rows read as columns.
  • Name the whole tracker once, in one sentence that covers every piece.
  • Show the count. Count done pieces only.
  • Drop to count only at narrow widths, decided by the host's own width.
  • Let the row say "ready" in words ("All five pieces in place").

Don't

  • Don't sort pips by state or fill them left to right like a bar.
  • Don't turn 5/5 green automatically. If completion colour is ever needed, pass it in, as Progress Bar does.
  • Don't make pips clickable, or put per-pip tooltips inside a tappable row.
  • Don't use more than 7 pips, or fewer than 3.
  • Don't add a live region when a state changes. The colour change runs on duration-fast and that's all.
  • Don't hide the tracker entirely on small screens.

Open questions

  1. Gap: keep the source's 3px (a one-off, 72px track), or snap to spacing-4 (76px) and drop the one-off?
  2. Not-started contrast: Neutral-3 is 1.42:1 on white, the same as the shipped Progress Bar track. Accept it, since it shows absence and the count carries the total, or add a ring? A ring blurs the line between it and the fix pip.
  3. Fix ring: Obsidian (proposed, 14:1, Stepper's amber + ink pairing) or Neutral-5 (6.9:1, quieter)?
  4. Count colour: OK to move from Neutral-6 to Neutral-9? Or should it be muted Neutral-5 / 400, like Progress Bar's trailing label?
  5. Lists: should "progress pips" join Lists' allowed trailing types, and should the queue row (pips + next step + CTA) become a Lists preset? It needs the amber-ink eyebrow first (scan item 9).
  6. Count only: is "3/5" alone clear enough in a narrow row, or should it read "3/5 pieces"?
  7. Draft shape: confirm A1, the hollow 1px Neutral-5 ring (now the default), over B dashed and C half-filled. Is hollow draft far enough from fix (amber fill + ink ring) in greyscale? See the Draft options greyscale column.
